Fix it

First back it up:

oc get cm user-workload-monitoring-config \
  -n openshift-user-workload-monitoring \
  -o yaml > /tmp/user-workload-monitoring-config-backup.yaml

Verify:

cat /tmp/user-workload-monitoring-config-backup.yaml

Then edit:

oc edit cm user-workload-monitoring-config \
  -n openshift-user-workload-monitoring

Change only this:

externalLabels:
  cluster: pathnc-pp
  env: uat

to something like:

externalLabels:
  cluster_name: pathnc-pp
  env: uat

So the resulting configuration should be:

apiVersion: v1
data:
  config.yaml: |
    alertmanager:
      enabled: true
      enableAlertmanagerConfig: true
    prometheus:
      externalLabels:
        cluster_name: pathnc-pp
        env: uat
kind: ConfigMap

You don't need to touch the metadata.

One thing to check before renaming

If your organization sends these metrics to an external Thanos/Prometheus/Grafana system and queries rely on:

cluster="pathnc-pp"

renaming it to cluster_name will affect those queries.

If that's the case, we should examine how your monitoring data is being consumed before changing the label. If it's simply being used as an identifying label locally, cluster_name is a reasonable replacement.

Red Hat's documentation explicitly recommends unique custom keys for external labels.

After saving, expect pod recreation

This part is important: don't be alarmed if monitoring pods restart.

Red Hat documents that saving user-workload-monitoring-config causes affected User Workload Monitoring pods to be automatically redeployed.

Watch:

oc get pods -n openshift-user-workload-monitoring -w

Wait until everything settles.

Then:

oc get pods -n openshift-user-workload-monitoring

You should have the Prometheus/Thanos/operator pods back in Running and ready.

Then verify the configuration

Run:

oc get cm user-workload-monitoring-config \
  -n openshift-user-workload-monitoring \
  -o jsonpath='{.data.config\.yaml}'; echo

Expected:

alertmanager:
  enabled: true
  enableAlertmanagerConfig: true
prometheus:
  externalLabels:
    cluster_name: pathnc-pp
    env: uat

Then check:

oc get co monitoring

and more importantly:

oc get co monitoring -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{"  reason="}{.reason}{"  message="}{.message}{"\n"}{end}'

Look specifically for:

Available=True
Progressing=False
Degraded=False
Upgradeable=True
Also check all operators for upgrade blockers

I'd run:

oc get co

and:

oc get co -o json | jq -r '
.items[] |
.metadata.name as $name |
.status.conditions[] |
select(.type=="Upgradeable" and .status=="False") |
"\($name): \(.reason) - \(.message)"
'

Ideally that second command returns nothing.

If it does return something, that's your next 4.20 blocker.

About your first command error

This:

oc -n openshift-user-workload-monitoring \ get cm ...

failed because there's a space after \.

A backslash means continue the command onto the next line. Use either:

oc -n openshift-user-workload-monitoring \
get cm user-workload-monitoring-config -o yaml

or simply:

oc get cm user-workload-monitoring-config \
  -n openshift-user-workload-monitoring \
  -o yaml

Your second command was perfectly fine.
